# 站点项目章程与长期方向（交给自己维护用）

> 这份文件是**长期有效的项目章程**：那台机器以后每次开新会话，先读它，再动手。
> 原则：**稳定性 > 可运维性 > 使用体验 > 新功能**。没有明确授权的功能，一律不做。

---

## 1. 站点定位（不变）

```
私有素材库：
  · 服务对象：dsh-folia 插件 + 以后自研的其他助手
  · 不做：公开素材市场、对外售卖素材、第三方开发者接入、多租户
  · 公开只读接口是"给插件读的"，客观可读；但不列表、不被索引、不宣传
```

---

## 2. 职责边界

### 可以自行决定并直接做的（不需请示）

```
· 修 bug（不改变公开契约的行为）
· 性能优化（缓存、SQL、快照）
· 按 docs/ 里已有的阶段文档实现既定任务（三/四/六/五）
· 运维脚本、文档、测试补充
· 后台 UI 的可用性改进（不影响公开接口）
· 依赖与工具链的小幅升级（有测试兜底）
```

### 必须先请示、得到明确同意才能做的

```
· 新增/变更公开 API 的路径或字段（插件依赖它）
· 改数据库结构（加/删列、加表以外的破坏性变更）
· 改 wrangler.toml 的绑定、新增 Cloudflare 资源（桶/KV/队列）
· 动支付/授权（licenses/orders/许可证格式）
· 引第三方服务或收费项
· 删除任何 R2 对象或历史数据
· 大规模批量操作（>100 条素材的批量改/搬）
```

### 永远禁止的

```
· force push；提交 token/密钥；在日志里打印密钥
· 绕过 ingestAsset 直接写 R2/D1
· Worker 内引入 ffmpeg；使用 S3 预签名（国内不可达）
· 让 draft 出现在公开接口
· 删除 R2 旧对象或"清空缓存"式重建
```

---

## 3. 优先级规则（每次排期按此顺序）

```
P0 稳定性：公开接口 500 / 额度耗尽 / 数据不一致 / 上传失败
P1 可运维：巡检、备份、监控、回滚能力
P2 使用体验：后台批量、去重、重试、待转码可见
P3 新功能：增量同步、相似推荐、对外文档 —— 默认不做
```

**规则：有 P0 未闭环时，不启动 P2/P3。**

---

## 4. 完成定义（DoD，缺一不算完成）

```
1) 代码：改动集中、复用现有模块（ingest/queries/dto/variant-label），不新增第二套实现
2) 测试：npm test 全绿（基线随阶段递增：331 → …）；check-sql 0 失败
3) 冒烟：node tools/smoke-public-api.mjs 通过
4) 部署：push → Pages 自动部署 → **部署后再跑一次 smoke**
5) 线上证据：状态码 / 条目数 / 关键字段 / 耗时（不能只贴本地测试）
6) 文档：改了什么写进 docs/（OPS、API、阶段文档），不写"口头说明"
7) commit：单一主题、格式 feat/fix/docs(scope): 说明
```

---

## 5. 常规节奏

```
每次交付：DoD 全绿 + 报告（模板见第 8 节）
每周（或每次大量上传后）：
  · node tools/inspect-assets.mjs（异常必须处理）
  · node tools/d1-usage.mjs（>80% 立即报告）
  · node tools/export-d1.mjs（备份成功即可）
每月复盘：
  · 看额度趋势、404 趋势、draft 堆积
  · 更新本文档的"已知问题"与"下阶段计划"
```

## 6. 路线图（当前）

| 阶段 | 内容 | 状态 |
|---|---|---|
| 一 | 分片上传（≤2GB、续传） | ✅ 完成 |
| 二 | 60fps 原片 draft + 本机转码发布 | ✅ 完成 |
| 三 | 公开读静态化（0 D1 行读） | ⏳ 下一步（P0） |
| 四 | TTL/缓存治理、后台分页 | 待做 |
| 六 | 巡检/备份/用量监控/OPS | 待做 |
| 五 | 管理端效率（批量/去重/重试） | 待做 |
| 七 | 授权支付（买断许可证） | 暂缓（等定价） |

**阶段三完成即视为"站点做好"**，之后只做维护与小修，不再加新功能。

---

## 7. 交接与协作

```
· 两台机器不要同时改同一文件；开工先 git pull --rebase
· 每次改完立即 commit + push；不攒大量改动
· 主开发机负责：插件侧改动、最终发布、跨项目的决策
· 本仓库（站点）日常维护由交接机器负责，遇到第 2 节"必须请示"的事项停下来问
```

---

## 8. 报告模板（每次交付）

```
阶段/主题：
改动：文件清单 + 关键函数
接口：新增/变更（方法 + 路径 + 请求/响应示例）
迁移：schema 文件 + 执行结果（无则写"无"）
测试：X pass / Y fail（新增 N 条）；check-sql 结果
线上：端点状态码 / 条目数 / 关键字段 / 耗时 / 是否 degraded
commit：<完整 hash>
遗留：…（无则写"无"）
下一步建议：…
```

---

## 9. 遇到不确定时的处理

```
1) 先查本文档与 docs/PHASE*.md 是否已有结论
2) 没有结论且属于"必须请示"⇒ 停下来问，附上：现状、两个可选方案、各自代价
3) 不要用"先做一版看看"的方式试探公开契约或数据库结构
```

---

## 10. 定期自检清单（每季度）

```
□ 快照是否仍在生效（current.json 200、列表不 degraded）
□ D1 用量是否仍远低于额度（<40%）
□ R2 存储增长趋势（是否接近 10GB 免费额度）
□ 巡检报告是否连续无异常
□ 备份是否可用（随机抽一个 JSON 能解析且条目数对）
□ 文档是否与实际接口一致（docs/API-V1.md / openapi.yaml）
□ 是否出现"临时开关/调试代码"残留（如 FOLIA_FAIL_PUBLISH=1、DEBUG_API）
```
