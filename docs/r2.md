# R2 模式

「R2 模式」= 站点仓库和构建产物里**不放任何壁纸文件**，所有图片/视频在 Cloudflare R2，元数据在 D1。换壁纸只写存储和数据库，不用重新部署。

这也顺带解决了 Pages 的两个硬限制：单次部署产物有大小上限，静态资源每次都要全量上传。

## 数据流

```
浏览器
  │  1. GET /                     → 静态 HTML/CSS/JS（Pages，几百 KB）
  │  2. GET /api/public/...       → D1：分类、标题、宽高、体积、R2 key
  │  3. GET /media/...  或  https://img.example.com/...
  │                                 → R2：原图 / 视频（按需、带缓存、支持 Range）
  ▼
Cloudflare
```

三条链路各自独立：改样式只动 Pages；传壁纸只动 R2 + D1；两者都不需要重建站点。

## Bucket 结构

```
folia-wallpapers/
└─ wallpapers/
   └─ wp_3f9a1c.../          ← 壁纸 id 前 12 位做目录，避免单目录过深
      └─ 9f3c1a2b3c4d5e6f.png ← key 里带内容哈希（sha256 前 16 位；历史 12 位对象保留不动）
```

为什么 key 里要带哈希：

- **天然防串**：换图必换 key，浏览器不会拿旧缓存；
- **可以 immutable**：`Cache-Control: public, max-age=31536000, immutable` 放心给一年；
- **去重**：同一张图重复上传，D1 里的唯一索引直接挡住。

> 前提是哈希取自**最终入库的那份字节**，且**永不覆盖同名 key**——否则这条保证就失效了，
> 详见下面「对象一致性守则」。

代价：替换文件后旧对象会变成孤儿。`PUT /asset` 已经会先删旧 key；如果上传到一半失败，可能残留，用 `tools/r2-audit.mjs` 对比 R2 与 D1 的 key（见下）。

> **上传资源请先看 [`docs/UPLOAD-SOP.md`](UPLOAD-SOP.md)**：键名怎么生成、七步流程、上传后四条验收命令、禁止清单。下面是原理和事故复盘。

## 对象一致性守则（2026-11-04 事故后新增）

### 三条硬规则

1. **键名必须由最终入库内容的哈希生成；内容一换，必须换键。**
   禁止在同一个 key 上覆盖上传。`/media/<key>` 的响应带 `cache-control: public, max-age=31536000, immutable`，
   边缘缓存和浏览器会把它当成"一年内不会变"。同名覆盖 ⇒ 边缘缓存（旧字节）与源站（新字节）
   长期并存 ⇒ 多连接/Range 下载会把两个版本拼成一个坏包。
2. **D1 的 `bytes` 与 `sha256` 必须来自同一份已校验的文件。**
   要么一起更新，要么都不更新。任何"只按 HEAD 长度校准 bytes、sha 留着旧值"的做法都会造出
   「bytes 属 A 版、sha256 属 B 版」的自相矛盾记录——比不修更糟，因为它会把真实故障伪装成"记录不准"。
3. **发现"同址双版本"时，取 D1 的 `sha256` 为准。**
   标准处理：`sha256` 对应的那一版是 canonical → 上传到**从未对外服务过**的新 key →
   对新 URL 三验（HEAD 长度、Range 0-99 的 `content-range` 总量、全量下载 sha256）→
   再改 D1 的 `storage_key`/`bytes`（`sha256` 不变）。

### 怎么发现（成本极低）

对同一条 URL 发两个请求，比较两个长度：

| 请求 | 实际走到哪 | 说明 |
|---|---|---|
| `HEAD`（不带 Range） | 可能命中**边缘缓存** | 反映"被缓存那一刻"的版本 |
| `GET` + `Range: bytes=0-0` | 一定**回源 R2** | 反映源站当前版本 |

两者不等 ⇒ 同一个 URL 上存在两个版本，**立即告警**，不要按其中任何一个去改 D1。
（`D:\folia-recover\integrity-cron.py` 已实现该探测，并把条目标 `missing_reason='dual-version'`。）

### 2026-11-04 排查结果：3 条 / 145 个 URL

全站 `GET /api/public/wallpapers`（110 条，含 assistant-skin / boot-animation / wallpaper，另含 variants 共 145 个 URL）
逐条做上面的对比，**只有这 3 条 zip 不一致**，其余 142 个 URL 两个长度一致：

| slug | 旧 key（保留不删，回滚/取证用） | 边缘全量 | 源站 Range | D1 canonical | 新 key |
|---|---|---|---|---|---|
| rainy-night | `wallpapers/wp_6b5017aa03bacabe67ec2f08/fd2b903f496c.zip` | 17,509,106 B / 10 entries（含 provenance） | 17,414,581 B / 9 entries | 17,509,106 B / `fd2b903f…` | `…/fd2b903f496c95e3.zip` |
| whalechan-harness | `wallpapers/wp_bd0377570d4aa8449e22ff3a/0a8e573fb1f8.zip` | 8,420,997 B / 74 entries（含 provenance） | 8,335,018 B / 73 entries | 8,420,997 B / `0a8e573f…` | `…/0a8e573fb1f81623.zip` |
| midnight-contract | `wallpapers/wp_2839c6ce6e7e72e76698606a/18dafa16017c.zip` | 14,434,632 B / 36 entries（含 provenance） | 14,237,267 B / 35 entries | 14,434,632 B / `18dafa16…` | `…/18dafa16017cbe3e.zip` |

规律：三个包都被"重新打包（删掉 `dsh-market.provenance.json`）"的版本覆盖过同一个 key。
canonical = 原始打包（含 provenance）那一版。`whalechan-harness` / `midnight-contract` 的 D1 `bytes`
曾被 HEAD 校准成无 provenance 版本的体积，与 `sha256` 矛盾，此次一并校正为 canonical 体积。

**key 前缀为什么是 16 位而不是 12 位**：这三条的旧 key 本身就是「sha256 前 12 位」，
但里面的内容已经被覆盖成别的版本。若仍用 12 位，新 key 会和旧 key **同名**，等于再次覆盖
immutable URL——正是这次故障本身。把哈希前缀扩到 16 位，得到从未对外服务过的 URL，
天然没有缓存污染。（**新写入统一 16 位**：`src/server/storage.js` 的 `assetKey()` / `thumbKey()`
已同步为 `slice(0, 16)`，`docs/UPLOAD-SOP.md` 按 16 位写；历史 12 位对象保留不动，不做批量改名。）

### 回滚与旧对象

**旧对象一律保留不删**，三条旧 key 仍在 R2 里（`…/fd2b903f496c.zip` 17,414,581 B、
`…/0a8e573fb1f8.zip` 8,335,018 B、`…/18dafa16017c.zip` 14,237,267 B），用于取证和回滚。

但注意：**这三条旧 12 位 key 在源站已经是"被覆盖后的版本"**，与 D1 里的 `sha256`/`bytes`
并不对应。所以"把 D1 的 `storage_key` 直接指回旧 key"**不是**可用的回滚——那会立刻重新制造
"记录与文件不一致"。真正的回滚 = 用留档的 canonical 文件重新上传（落到任意从未服务过的新 key）：

| slug | 留档文件 | 体积 | sha256 |
|---|---|---|---|
| rainy-night | `D:\folia-recover\rainy-night-versions\edge-full.zip` | 17,509,106 | `fd2b903f496c…` |
| whalechan-harness | `D:\folia-recover\rainy-night-versions\wp_bd0377570d4aa8449e22ff3a.edge-full.zip` | 8,420,997 | `0a8e573fb1f81623…` |
| midnight-contract | `D:\folia-recover\rainy-night-versions\wp_2839c6ce6e7e72e76698606a.edge-full.zip` | 14,434,632 | `18dafa16017cbe3e…` |

同目录下的 `origin-range.zip` / `wp_*.origin-range.zip` 是**无 provenance 的另一版**，只作对比留档，不要拿来回滚。

### 工具链同步修掉的坑

- `D:\folia-recover\fix-d1-size.py`：`--head-only` 从"用 HEAD 长度改 bytes"降级为**纯探测、禁止写库**；
  长度不符时只提示"先下载整包比对 sha256，bytes 与 sha256 必须成对更新"。
- `D:\folia-recover\integrity-cron.py`：长度不符**不再直接 UPDATE bytes**，改为
  ①HEAD vs Range 不一致 → 标 `missing_reason='dual-version'`；
  ②长度自洽但与 D1.bytes 不符 → 标 `missing_reason='size-drift'`；修复后自动清除标记。

## 三种出图方式

| 方式 | 地址 | 何时用 | 注意 |
|---|---|---|---|
| Worker 出图 | `/media/<key>` | 已经默认可用，零配置 | 每张图都算一次 Worker 请求 |
| R2 自定义域名 | `https://img.example.com/<key>` | **推荐**，正式站点 | 需要你自己的域名接入 Cloudflare |
| R2 公共开发域名 | `https://pub-xxxx.r2.dev/<key>` | 临时测试 | 有限速，不能当生产用 |

切换到自定义域名只要一个变量，代码不用改：

```toml
# wrangler.toml
[vars]
MEDIA_BASE = "https://img.example.com"
```

之后 `/api/public/wallpapers` 返回的 `url` 会变成 `https://img.example.com/wallpapers/...`，前端照旧用。没设就回落到 `/media/...`，所以可以先上线、后切域名。

> 为什么建议切：Worker 免费额度是每天 10 万请求。壁纸站一屏 24 张图，一天几千访问就穿；自定义域名出图不经过 Worker，只算 R2 Class B 操作（$0.36/百万次）。

## 缓存与 Range

- 图片/视频一律 `immutable`，一年。因为 key 带哈希，这是安全的。
- 视频支持 `Range`（`/media/*` 路由里实现了 206），播放器拖进度条不会整段重下。
- 自定义域名方式下，缓存由 R2 的 `Cache-Control` 元数据带出——上传时已经写好了（`src/server/storage.js`）。

## 公开还是私有

现在默认是**公开可读**：任何拿到 key 的人都能访问。壁纸站通常就是这样（要能复制直链去当壁纸）。

如果以后要「仅登录可见」：

- R2 关掉公共访问；
- 改成签发预签名 URL（`env.BUCKET.get()` 之后 `createPresignedUrl` 需要 S3 API，Worker 里不能直接用）；
- 或者继续走 `/media/<key>`，在路由里加一层会话校验再 `BUCKET.get()`。

第二条最省事，但会回到「每张图一次 Worker 请求」的成本模型。想清楚了再改，别两头都占。

## 迁移现有图片

如果旧站图片现在散在仓库或别的图床里：

```bash
# 走 API 导入（推荐：会自动去重、读宽高、写 D1）
FOLIA_URL=https://folia-5ve.pages.dev \
FOLIA_EMAIL=admin@example.com \
FOLIA_PASSWORD='******' \
node tools/import-wallpapers.mjs ./old-wallpapers --category dynamic --publish
```

想跳过 Worker 直接灌 R2 也可以，但要自己补 D1 行，容易漏 `sha256` 和宽高，不推荐：

```bash
npx wrangler r2 object put folia-wallpapers/wallpapers/wp_x/abc.png --file=./abc.png
```

## 成本估算

按 2000 张壁纸、平均 6MB 算（约 12GB）：

| 项目 | 计费 | 估算 |
|---|---|---|
| 存储 | $0.015 / GB·月 | 12GB ≈ **$0.18/月** |
| Class B（读） | $0.36 / 百万次 | 10 万次/月 ≈ **$0.04** |
| Class A（写） | $4.50 / 百万次 | 2000 次上传 ≈ **$0.01** |
| 出网流量 | **免费** | $0 |

R2 的卖点就是出网免费——壁纸站是典型的高流量低写入场景，这是它比 S3 便宜一个数量级的地方。价格以官网为准，这里只给量级。

## 备份与清理

```bash
# 全量镜像到本地（rclone 配 R2 的 S3 兼容端点）
rclone sync r2:folia-wallpapers ./backup/folia-wallpapers

# 反过来恢复
rclone sync ./backup/folia-wallpapers r2:folia-wallpapers
```

不建议用 R2 生命周期规则自动删：壁纸是用户资产，删错了没处找。要清理孤儿对象，先比对：

```bash
npx wrangler d1 execute folia --command "SELECT storage_key FROM wallpapers" --remote --json > keys.json
```

然后拿 `keys.json` 和 `rclone lsf r2:folia-wallpapers --recursive` 求差集，人工确认后再删。

## 一个必须知道的取舍

现在列表页加载的是**原图**。4K 壁纸 8MB，一屏 24 张就是 190MB——首屏在移动网络下会很难受。

`img` 上的 `loading="lazy"`、`decoding="async"`、显式 `width/height` 只能缓解，不能解决。真正的解法是缩略图变体：

- 上传时用 sharp 生成 480w 的 WebP 存到 `thumbs/` 前缀，列表用缩略图，点开才加载原图；
- 或者接 Cloudflare Images，用 `?width=480` 变体。

这件事我**没有做**，因为它会改动上传链路和数据模型，属于下一步。但如果你现在就要上线给真实用户看，这是优先级最高的一件事。
